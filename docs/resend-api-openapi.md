# Resend REST API OpenAPI source

`plugins/resend-api/` is a separate API-key publication candidate (`resend-api@1.0.0`), not the existing `resend@1.0.2` hosted MCP OAuth integration. Its unmodified JSON source is pinned from `https://resend.com/openapi.json` by byte digest in `openapi-source.json`. Every selected tool defaults to `allow`; GET is classified read, DELETE destructive, and POST/PATCH write. The `POST /emails` tool sends email with Resend's full admitted JSON body shape and optional `Idempotency-Key` header (max 256 characters). The compiler does not generate an idempotency key or retry the request. API-key creation and deletion are included and classified write/destructive respectively; do not mistake them for reads.

The selection contains **59 nondeprecated operations** from 83 upstream operations. These cover email sending/list/detail/update/cancel/batch; domains; API keys; contacts; broadcasts; templates (read/publish/duplicate/delete); segments; topics; contact properties and membership; events (except send); logs (list); and automations (list). Their method/path-derived operation identities are stable under source reordering. The selection retains the upstream JSON byte-for-byte and the full supported send request body, including recipient string-or-array forms and template variable string-or-number values. OpenAPI examples, defaults, and `deprecated` flags are nonvalidation annotations. The `binary` attachment-content format is represented as a JSON string with **no binary/base64 conversion** by the compiler or runtime; provider-specific content encoding and live behavior require validation before publication. Other unsupported formats remain rejected rather than being silently weakened.

**Excluded operations:** Four upstream operations are marked deprecated: `POST /audiences`, `GET /audiences`, `GET /audiences/{id}`, and `DELETE /audiences/{id}`. The following 20 are rejected by the compiler with `openapi-schema-unsupported` because their request parameter/body schemas use format or composition/value shapes outside the app-owned contract (not merely because they are reads):

The source is `reviewed-publishable` and release-index `publicationEligible: true`. Independent source and authority review approved the exact `resend-api@1.0.0` release in `releases/reviews/supernala-public__supernala__resend-api__1.0.0.json`; this approval is not a published version. The supervisor provisioned the credential-free production provider registration `resend-api-credentials-v1` with publication authorization and verified its read-only D1 projection: active revision 1, provider `supernala/resend-api`, resource `https://api.resend.com`, legacy `dynamic` registration mode, metadata and callback URLs `https://api.resend.com`, empty approved scopes, platform source, and null OAuth definition and client-credential reference. The registration is a metadata prerequisite, not evidence of live Resend API acceptance or OAuth authority. Production publication still requires a fresh verified baseline and the trusted release workflow; live API and installation acceptance remain pending. The OpenAPI authoring contract has no icon field; any reuse of the hosted Resend icon belongs to the application/store asset mapping and must be verified there. No API key, provider invocation, or publication is performed by this source.
